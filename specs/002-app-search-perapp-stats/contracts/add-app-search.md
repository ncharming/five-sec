# Contract: 添加应用搜索选择器

**Spec**: [spec.md](../spec.md) · **Plan**: [plan.md](../plan.md) · **Data Model**: [data-model.md](../data-model.md)

定义 `AppListScreen` 添加应用选择器（基于既有 `AlertDialog`）的 UI/行为契约。覆盖 spec FR-001~006、User Story 1 的全部验收场景。

## 触发

用户在应用清单页点 `+`：
- 若目标清单已达 3 个上限 → 显示"最多可添加3个应用…"提示（001 既有逻辑，不改）。
- 否则 → 打开本搜索选择器。

## 选择器结构（自上而下）

1. **标题**：「添加应用」
2. **搜索框（新增）**：单行 `TextField`，占位文案如"搜索应用名称或包名"，可清空。
3. **候选列表**：`LazyColumn`，展示过滤后的 `InstalledApp` 项；每项显示应用友好名称（`label`）。
4. **完成按钮**：关闭选择器（既有）。

## 搜索行为契约

| 规则 | 行为 |
|------|------|
| 实时过滤（FR-002） | 用户输入即触发过滤，无需提交按钮；过滤在内存缓存列表上做纯函数计算 |
| 名称匹配（FR-002） | 按 `label` 不区分大小写的子串包含匹配 |
| 包名匹配（FR-003） | 同时按 `packageName` 子串包含匹配（满足技术定位/重名场景） |
| 大小写/空格 | 不区分大小写；关键词首尾空格 `trim` 后参与匹配 |
| 清空（US1-3） | 清空搜索框 → 列表恢复显示全部可添加应用 |
| 空结果（FR-004） | 过滤结果为空 → 列表区显示友好空状态"未找到匹配的应用"，非空白 |
| 去重（FR-005） | 已在目标清单中的应用：仍可出现（便于用户确认），但**置灰且不可点击**（标识"已添加"）；过滤命中时照常过滤 |

## 选择与上限交互

- 点击一个**未添加**的候选 → 调 `AppListViewModel.add(packageName, now)` → 经 `TargetAppRepository.addNewApp()`（含 3 上限校验）→ 成功则关闭选择器并刷新清单。
- 选择器打开时已在上限内（< 3）；若并发导致越界，按 001 既有 `addNewApp` 返回失败处理（日志 + 不添加）。

## 性能契约（FR-006 / SC-001）

- 候选列表首次加载在 `Dispatchers.IO` 完成（不在主线程枚举 `PackageManager`）；加载中可显示轻量 loading。
- 加载结果在 ViewModel 内缓存；输入过滤为内存操作，p90 < 0.5s（200+ 应用设备）。
- 列表用 `LazyColumn`（仅渲染可见项），不一次性组合全部候选。

## 验收映射

- US1-1（加载显示全部 + 搜索框）→ 选择器结构 1~3
- US1-2（输入名称实时过滤）→ 名称匹配 + 实时过滤
- US1-3（清空恢复全部）→ 清空规则
- US1-4（包名搜索）→ 包名匹配
- US1-5（无匹配空状态）→ 空结果
- US1-6（已添加去重/置灰）→ 去重
- US1-7（选择加入 + 上限）→ 选择与上限交互
